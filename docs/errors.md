# Errors

ntex uses the [`ntex::web::WebResponseError`][responseerror] trait for error handling from web handlers.

If a handler returns an error (any type implementing the [general Rust trait `std::error::Error`][stderror]) in a `Result` and that error also implements the `WebResponseError` trait, ntex will render that error as an HTTP response. An internal server error is generated by default:

```rust
pub trait WebResponseError<St, Err>: std::error::Error + 'static {
    fn error_response(&self, state: &St) -> HttpResponse;
}
```

`St` is the application state type and `Err` is the application's error domain, defined by the state's `web::State::Error` type. The default error domain is [`web::DefaultError`][defaulterror]. To make an error usable with any application state, implement `WebResponseError<St, web::DefaultError>` for all `St`.

A `Responder` coerces compatible `Result`s into HTTP responses:

```rust
impl<St, T, E> Responder<St> for Result<T, E>
where
    St: web::State,
    T: Responder<St>,
    E: WebResponseError<St, St::Error>,
```

Errors from services and middleware are stored in the type-erased [`web::WebError`][weberror] type. Any error that implements `WebResponseError` can be converted to one automatically.

ntex provides `WebResponseError` implementations for some common non-ntex errors. For example, if a handler responds with an `io::Error`, that error is converted into an internal server error response:

```rust
use std::io;
use ntex_files::NamedFile;

async fn index(_req: HttpRequest) -> io::Result<NamedFile> {
    Ok(NamedFile::open("static/index.html")?)
}
```

See [the ntex API documentation][responseerrorimpls] for a full list of foreign implementations for `WebResponseError`.

## Error logging

ntex logs errors that are rendered as _500_ (internal server error) responses at the `ERROR` log level, all other errors are logged at the `DEBUG` log level. Logging is configurable with environmental variables:

```
>> RUST_LOG=ntex=debug cargo run
```

## Recommended practices in error handling

It might be useful to think about dividing the errors an application produces into two broad groups: those which are intended to be user-facing, and those which are not.

However, sending back an error's message isn't desirable for all errors -- there are many failures that occur in a server environment where we'd probably want the specifics to be hidden from the user. For example, if a database goes down and client libraries start producing connect timeout errors, or if an HTML template was improperly formatted and errors when rendered. In these cases, it might be preferable to map the errors to a generic error suitable for user consumption.
